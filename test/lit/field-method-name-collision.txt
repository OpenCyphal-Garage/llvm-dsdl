# Regression: a DSDL field named the same as a generated method (`serialize` / `deserialize`) is
# spec-valid (not a language keyword, so the frontend accepts it) but collides with the type's methods
# in Go (a struct field and method cannot share a name -> compile error), C++ (a data member and a
# member function cannot either) and Python (a dataclass attribute shadows the method, so
# `self.serialize()` tries to call an int at runtime). Rust (fields and inherent methods occupy
# separate namespaces) and TypeScript (free functions, not members) are unaffected.
#
# The names the generated code claims are part of the naming policy rather than of any one scope, so
# such a field is escaped to `Serialize_` / `serialize_` while the method keeps its name. The escape
# was `Serialize_2` until the claimed-name policy landed: that spelling came from the collision
# repair, which means "the second name wanting this identifier" and was the wrong thing to say about
# a name no other field was competing for.

# RUN: printf 'uint8 serialize\nuint8 deserialize\n@sealed\n' > %t/dsdl/mf/M.1.0.dsdl
